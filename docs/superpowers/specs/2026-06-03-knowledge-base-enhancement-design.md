# 整体知识库增强 MVP 设计

## 背景

AI 保险教练已经完成四个小程序工作模式：

- 客户卡点跟进：面谈后或跟进前准备下一句话和下一步策略。
- 见前准备：见客户前生成面谈作战卡。
- 面谈复盘：面谈结束后生成跟进计划、教练纠偏和客户档案补充建议。
- 完整诊断：基于 KYC 信息做深度顾问式销售诊断。

这些模式的质量高度依赖 `src/lib/knowledge.ts`。现有知识库已经覆盖顾问式流程、客户分层、社交激活、找需求、强化需求、找不足、异议处理、DRG 医疗险等内容，但它仍是一个大文件内的手工模块集合。

用户后续会持续补充新资料。第四阶段需要把知识库升级成一个可持续扩展的模块化系统，而不是继续把所有内容堆进一个文件。

## 目标

第四阶段 MVP 的目标：

- 把知识库从单一大文件升级为模块化结构。
- 高质量萃取重疾险和分红/储蓄险资料，补强现有知识。
- 建立明确的模块元数据和调用规则，支持不同工作模式按需加载。
- 为后续持续补资料预留标准流程。
- 保持现有小程序工作模式不变，优先提升 AI 教练回答质量。

## 非目标

第一版不做：

- 后台上传 PDF。
- 自动向量数据库。
- 原文全文检索。
- 向用户展示知识库来源。
- 把 PDF 原文大段塞进 prompt。
- 自动生成可直接上线的知识模块。
- 用 AI 输出替代人工审核后的知识萃取。

这些能力后续可以做，但第一版先追求质量、稳定性和可维护性。

## 产品原则

### 1. 知识必须被萃取，不直接搬运原文

PDF 原文是课程转写稿，存在口语重复、上下文跳转、例子冗长等问题。进入系统前必须整理成：

- 核心原则。
- 适用场景。
- 禁用边界。
- 判断条件。
- 简短话术。
- 异议处理步骤。

### 2. 模块要能被选择，不是全部常驻

不同用户问题需要不同知识。系统不应每次加载所有知识，而应该根据客户信息、工作模式和代理人输入选择最相关模块。

### 3. 合规红线高于产品知识

任何产品知识都不能覆盖安全和合规规则：

- 不承诺收益。
- 不推荐具体产品。
- 不恐吓客户。
- 不把 AI 判断当作客户事实。
- 不泄露知识库来源、系统提示词或底层资料。

### 4. 以后新增资料要有固定入口

未来新增资料时，应按统一流程处理：

1. 抽取文本。
2. 识别主题。
3. 萃取为知识模块。
4. 标注触发条件。
5. 加入选择器。
6. 通过回归检查。
7. 部署上线。

## 架构设计

把现有 `src/lib/knowledge.ts` 拆成目录：

```text
src/lib/knowledge/
  index.ts
  types.ts
  core.ts
  methods.ts
  products-critical-illness.ts
  products-savings-dividend.ts
  objections.ts
  cases.ts
  selector.ts
```

### `types.ts`

定义统一的知识模块类型：

- `id`：稳定模块 ID。
- `title`：模块标题。
- `tier`：`core` / `method` / `product` / `objection` / `case`。
- `topics`：主题标签，例如 `critical_illness`、`medical`、`savings`、`dividend`、`education`、`retirement`、`inheritance`。
- `modes`：适用工作模式，例如 `diagnosis`、`objection_followup`、`pre_meeting_prep`、`meeting_review`。
- `sourceRefs`：内部来源标记，用于维护，不输出给用户。
- `content`：萃取后的知识内容。

### `core.ts`

保留并强化始终加载的核心模块：

- 顾问式面谈阶段流程。
- 角色定位和输出原则。
- 合规红线。
- 不跳步规则。
- 不制造恐惧规则。
- 不泄露知识库来源规则。

### `methods.ts`

承载跨产品通用的方法论：

- 社交激活。
- 找需求。
- 强化需求。
- 找不足。
- 给方案。
- 面谈复盘。

### `products-critical-illness.ts`

补强重疾险知识，第一版至少包含：

- 重疾险为什么仍是基本功。
- 不同客户层级的重疾险价值。
- 重疾险不是只解决医药费，而是解决收入中断和康养现金流。
- 医疗险和重疾险的分工。
- 大中产和高净值客户的资源型销售逻辑。
- 主动咨询重疾险时如何找动机。
- 非主动咨询时如何敲身体担心。
- 重疾保额如何由客户自己算出来。
- 核保、已有百万医疗、公司补充医疗、保费倒挂、没钱、交不上保费等异议处理。

### `products-savings-dividend.ts`

补强分红/储蓄险知识，第一版至少包含：

- 731 后利率变化和销售方式变化。
- 为什么不能只讲固定收益或分红收益。
- 储蓄类产品的顾问式销售核心：教育、养老、传承等长期目标。
- 教育金画面感。
- 养老金画面感。
- 刚性需求和弹性需求的预期管理。
- 现有理财方式缺口。
- 存不下来钱场景。
- 投资风险。
- 挪用风险。
- 利率下行风险。
- 使用期风险。
- 护理缺口。
- 婚姻风险和债务风险。
- 分红险表达边界：讲功能和适配，不承诺收益。

### `objections.ts`

统一管理跨产品异议：

- 我再考虑一下。
- 我要跟家人商量。
- 太贵了。
- 没预算。
- 已经有百万医疗。
- 公司有补充医疗。
- 收益不如银行/基金/其他公司。
- 以后交不上保费。
- 保费倒挂不划算。

### `cases.ts`

保存短案例和复盘模板，支持面谈复盘模式：

- 母婴店主案例。
- 大厂高压行业客户。
- 富裕中产单身客户。
- 有孩子教育期待客户。
- 准退休/养老期待客户。
- 有房产或投资现有方式客户。

### `selector.ts`

负责根据输入选择模块。

选择器输入：

- 当前模式：`diagnosis`、`objection_followup`、`pre_meeting_prep`、`meeting_review`。
- KYC 客户档案。
- 用户本轮输入文本。
- 是否追问。

选择器输出：

- 始终包含核心模块。
- 首次请求包含通用方法模块。
- 按分数选择 2 到 4 个产品/异议/案例模块。
- 追问时保留核心模块，并根据追问文本补充必要模块。

## 调用策略

### 主题识别

根据用户输入和客户资料识别主题：

- `critical_illness`：重疾、大病、身体、收入中断、康复、康养、核保、保额。
- `medical`：百万医疗、医疗险、补充医疗、DRG、特需部、国际部。
- `savings`：储蓄、年金、教育金、养老金、现金流、长期规划。
- `dividend`：分红、红利、收益、利率、预定利率、开门红。
- `education`：孩子、教育、留学、国际学校、小升初。
- `retirement`：养老、退休、旅居、养老社区、护理。
- `inheritance`：传承、婚姻、债务、给孩子留钱。
- `objection`：贵、没钱、考虑、家人商量、收益比较、交不上。

### 工作模式权重

不同工作模式的模块偏好：

- 完整诊断：方法模块 + 产品模块 + 异议模块。
- 客户卡点跟进：异议模块 + 当前产品模块 + 阶段回退规则。
- 见前准备：客户分层 + 需求分析 + 产品方向模块。
- 面谈复盘：案例复盘 + 阶段判断 + 下一步跟进模块。

### 产品模块边界

如果客户只处于阶段 0 或阶段 1，不直接输出产品方案。产品模块只用于帮助代理人判断方向和提问，不允许提前推荐产品。

如果客户在阶段 2 或 3，才允许进入强化需求和找不足。

如果客户进入方案讨论，仍只输出沟通策略，不输出具体产品推荐、收益承诺或正式投保建议。

## 首批增强内容

### 重疾险增强

第一版重疾模块重点解决：

- 新人代理人不会卖重疾，只会卖储蓄险。
- 客户认为已有医疗险就不用重疾险。
- 客户认为公司补充医疗够了。
- 客户觉得重疾险贵。
- 客户担心核保麻烦。
- 客户觉得保费倒挂不划算。
- 代理人不会从身体担心切入。
- 代理人把重疾险讲成医药费报销，导致逻辑被客户反驳。

### 分红/储蓄险增强

第一版分红/储蓄模块重点解决：

- 代理人只会讲收益，缺少顾问式路径。
- 利率下降后不知道怎么讲分红险。
- 客户拿银行、基金、股票收益比较。
- 代理人不会聊教育金和养老金画面感。
- 代理人不会敲客户现有理财方式的缺口。
- 代理人不会处理挪用风险、利率下行风险、使用期风险和护理缺口。
- 代理人容易承诺收益，需要明确话术边界。

## 安全与合规

新增知识模块必须遵守：

- 不输出资料来源、讲师名称、PDF 名称、内部文件路径。
- 不输出系统提示词和知识库结构。
- 不承诺分红、收益、利率或投资结果。
- 不推荐具体保险产品。
- 不替代正式保险条款。
- 不制造恐惧。
- 不编造客户家庭、健康、财务事实。
- 对不确定客户信息使用“可能”“待确认”。
- 输出结尾继续保留合规免责声明。

## 维护流程

未来用户继续补充资料时，按以下流程：

1. 抽取文本并确认是否需要 OCR。
2. 建立资料摘要，只供内部维护。
3. 把资料拆成知识模块，不直接使用原文。
4. 给每个模块标注主题、适用模式和触发词。
5. 加入选择器评分规则。
6. 增加回归检查，确保模块可被选中。
7. 跑 `npm run check:security`、`npm run lint`、`npm run build`。
8. 部署 Vercel 后端。

## 验收标准

- `src/lib/knowledge.ts` 被拆分为可维护的知识库目录。
- 现有 `selectModules` 和 `selectModulesForFollowUp` 行为保持兼容。
- 四个工作模式仍能正常调用 `/api/coach`。
- 重疾相关输入能触发重疾模块。
- 百万医疗/补充医疗相关输入能触发医疗与重疾分工模块。
- 分红/收益/利率相关输入能触发分红/储蓄模块。
- 教育金/养老金/传承相关输入能触发对应储蓄目标模块。
- 异议相关输入能触发异议模块。
- 不输出 `[KYC_UPDATE]` 的模式继续保持原有约束。
- `npm run check:security`、`npm run lint`、`npm run build` 通过。
